scalert_event — სრული დოკუმენტაცია

English version · გამართვის ინსტრუქცია

scalert_event ავტომატურად აგზავნის შეტყობინებას SeisComP-ის მიწისძვრაზე. scalert იძახებს ჩვენს სკრიპტს და გადასცემს event_id-ს. სკრიპტი SeisComP-ის ბაზიდან იღებს მიწისძვრის პარამეტრებს და წესების მიხედვით წყვეტს, ვის ეგზავნება შეტყობინება. შემდეგ აგზავნის მეილს და SMS-ს, მიწისძვრას ამატებს iesdata საიტზე და, საჭიროებისას, აქვეყნებს WordPress-ზე.

ეს დოკუმენტი აღწერს, როგორ მუშაობს სისტემა. ინსტალაცია, .env-ის შევსება და პრობლემების გადაჭრა აღწერილია გამართვის ინსტრუქციაში.

პრინციპი: გადაწყვეტილება და გაგზავნა ცალ-ცალკეა. automate_events მხოლოდ წყვეტს და არაფერს აგზავნის. send_notification და send_eq2api მხოლოდ აგზავნიან და არაფერს წყვეტენ. ამიტომ ახალი წესი მხოლოდ rules.py-ში ემატება, ახალი არხი (მაგ. Telegram) კი ცალკე მოდულად. ერთი მეორეზე გავლენას არ ახდენს.

არხები ერთმანეთს არ აჩერებენ. თუ ერთი ჩავარდა, დანარჩენები მაინც იგზავნება, ხოლო ჩავარდნა ლოგში და გამოსვლის კოდში ჩანს.

2. როგორ იძახებს scalert სკრიპტს

scalert მიწისძვრის შექმნისას და ყოველი განახლებისას უშვებს scripts.event-ში მითითებულ სკრიპტს შემდეგი არგუმენტებით:

არგუმენტი მნიშვნელობა
$1 ტექსტური შეტყობინება (scalert-ის ფორმატით)
$2 1 — ახალი მიწისძვრა, 0 — განახლება
$3 მიწისძვრის publicID, მაგ. ies2026rudf — ეს არის event_id
$4 arrival-ების (ფაზების) რაოდენობა
$5 მაგნიტუდა (შეიძლება არ იყოს)

სკრიპტი მხოლოდ $3-ს ეყრდნობა. $1, $2, $4 და $5 ლოგში იწერება, მაგრამ გადაწყვეტილებისთვის ყველა პარამეტრი ბაზიდან იკითხება, რომ ერთ წყაროს ეყრდნობოდეს.

ხელით გაშვება (scalert-ის გარეშე):

./scalert_event.py ies2026rudf
./scalert_event.py --dry-run ies2026rudf     # წყვეტს და წერს ლოგს, არაფერს აგზავნის

3. შესვლის წერტილი: scalert_event.py

მხოლოდ ნაბიჯებს აერთებს, ბიზნეს-ლოგიკა აქ არ არის:

  1. კითხულობს არგუმენტებს და წერს RECEIVED;
  2. process(): ბაზიდან წაკითხვა → გადაწყვეტილება → არხები;
  3. თითო არხს ცალკე იძახებს. ერთის შეცდომა დანარჩენებს არ აჩერებს;
  4. წერს DONE-ს და აბრუნებს გამოსვლის კოდს.
კოდი მნიშვნელობა
0 დამუშავდა: გაიგზავნა, ან გადაწყდა, რომ არ იგზავნება
1 შეცდომა: მიწისძვრა ბაზაში ვერ მოიძებნა, ან რომელიმე არხი ჩავარდა შეცდომით
2 არასწორი არგუმენტები

არხის შეცდომად ითვლება API-ის შეცდომა (EventApiError), მიმღებების ფაილის შეცდომა (RecipientsError) და ნებისმიერი მოულოდნელი შეცდომა. თუ SMTP ან SMS-ის ყველა პროვაიდერი ვერ აგზავნის, ეს ლოგში იწერება (MAIL FAILED, SMS FAILED), მაგრამ DONE-ში ჩანს როგორც not_sent და გამოსვლის კოდს არ ცვლის.

4. მონაცემები SeisComP-ის ბაზიდან: seiscomp_db.py

load_event(event_id) -> EventData

Event (publicID = event_id)
  ├── preferredOriginID     ──► Origin: time, latitude, longitude, depth, evaluationMode
  └── preferredMagnitudeID  ──► Magnitude (preferred)
Origin._oid ──► Magnitude._parent_oid: ამ origin-ის ყველა მაგნიტუდა (ML, MLv, M, mb, ...)
  • გამოიყენება Event.preferredOriginID და არა ყველაზე ახალი origin, რადგან preferred origin-ს SeisComP თავად თვლის საუკეთესოდ;
  • SQL მოთხოვნები პარამეტრიზებულია (cursor.execute(sql, (event_id,)));
  • რბოლის პირობა. scalert მიწისძვრას messaging-იდან იღებს, scdb კი ბაზაში ასინქრონულად წერს. ამიტომ მიწისძვრა ან მისი origin შეიძლება ბაზაში ჯერ არ იყოს. load_event ცდილობს SC_DB_RETRIES-ჯერ (ნაგულისხმევად 5), SC_DB_RETRY_DELAY წამის (3) პაუზით, და ლოგში წერს WAITING. თუ ვერ იპოვა, ჩნდება EventNotReady, ლოგში კი ერთი ხაზი: FAILED event_id=...: event ... not found.

EventData:

ველი ტიპი აღწერა
event_id str publicID
origin_id str preferred origin-ის publicID
origin_time datetime UTC
latitude, longitude float გრადუსი
depth float კმ; თუ SeisComP-ში არ არის, 0.0
evaluation_mode str automatic / manual
event_type str | None not existing, not locatable, outside of network interest → SKIPPED
magnitudes dict[str, float] მაგ. {"ML": 3.4, "MLv": 3.3, "M": 3.4}
preferred_magnitude_type str | None preferred მაგნიტუდის ტიპი
